> 对应「描述.md」第五节（固件开发）、第六节（通信协议）、第九节（实现细节）。

## 一、问题根因分析

### 1.1 LEDC / PWM 初始化失败

**现象**：串口报错 `No more LEDC channels available! (maximum 8) or bit width too big (maximum 14)`，舵机 PWM 无输出。

**根因（已确认）**：

| 参数 | 当前值 | ESP32-S3 硬件上限 | 结果 |
|------|--------|-------------------|------|
| SERVO_RES_BITS | **16** | **14** | `ledcSetup()` 直接返回 0，timer 未配置 |
| MOTOR_RES_BITS | 10 | 14 | 正常 |

ESP32-S3 的 LEDC 硬件限制为 14 位分辨率（`SOC_LEDC_TIMER_BIT_WIDE_NUM = 14`）。当前代码舵机使用 16 位，`ledcSetup(channel, freq, 16)` 在第一条检查就失败：

```c
// esp32-hal-ledc.c:59
if(chan >= LEDC_CHANNELS || bit_num > LEDC_MAX_BIT_WIDTH){
    log_e("No more LEDC channels available! ...");
    return 0;  // ← 直接失败，timer 从未配置
}
```

**连锁影响**：

1. `ledcSetup` 失败后 `ledcAttachPin` 仍然执行，将 GPIO5 绑定到一个未配置的 LEDC 通道
2. 后续每次 `ledcWrite(channel1, duty)` 向无效通道写数据，可能触发 LEDC 底层异常
3. 舵机 `writePulse()` 计算用 `_maxDuty = (1<<16)-1 = 65535`，但实际 timer 是 14 位硬件，duty 值完全错位
4. 状态灯（NeoPixel）也用 LEDC 通道，通道竞争可能产生干扰

**影响范围**：`servo.cpp`、`servo.h`、`config.h`（SERVO_RES_BITS）

---

### 1.2 WiFi AP DHCP 不分配 IP

**现象**：手机关联 AP 成功（日志显示 `设备已关联 MAC=... AID=1`），但永远拿不到 IP。无 `STAIPASSIGNED` 事件。

**已尝试的修复（均未生效）**：

1. ✗ `WiFi.disconnect(true,true)` + `WIFI_OFF` 清理后再开 AP
2. ✗ 显式 `WiFi.softAPConfig(ip, gw, mask)` 配置网络参数
3. ✗ `WiFi.setSleep(false)` 关闭省电
4. ✗ `WiFi.persistent(false)` 禁止 flash 持久化
5. ✗ `esp_netif_dhcps_start()` 强制启动 DHCP 服务器

**根因分析**：

通过追踪 Arduino-ESP32 源码发现：

- `WiFi.softAP(ssid)` **只设置 SSID 和认证**，不启动 DHCP
- DHCP 服务器在 `WiFi.mode(WIFI_AP)` → `esp_wifi_start()` 时由 netif 层自动启动
- 当前代码的初始化序列（mode → softAPConfig → softAP）中，`softAPConfig()` 会 stop 再 start DHCP，可能在 WiFi 尚未完全就绪时执行，导致 DHCP 服务器状态异常

更关键的是：**初始化顺序问题**。当前 `main.cpp` 的启动顺序：

```
g_storage.begin()     →  配置加载
g_winder.begin()      →  LEDC 初始化（舵机失败！）→ 传感器中断挂载
g_led.begin()         →  NeoPixel 初始化
g_comms.begin()       →  WiFi 初始化（此时系统已处于异常状态）
g_winder.goHome()     →  舵机开始向无效通道写 PWM
```

`g_winder.begin()` 中舵机 `ledcSetup` 失败后，`ledcAttachPin` 仍执行，GPIO5 绑定到无效通道。此后每次 loop 中 `g_servo.moveHome()` → `ledcWrite` 向无效通道持续写入。**LEDC 硬件模块的异常状态可能干扰了共享外设总线，间接影响 WiFi 射频初始化**。

此外，NeoPixel `show()` 会短暂禁用中断（WS2812 时序要求），虽然单像素仅 ~30μs，但在 WiFi DHCP 关键窗口期如果恰好碰撞，可能导致 DHCP 包丢失。

## 二、方案决策

### 对比

| 方案 | 改动量 | 可靠性 | 维护难度 | 推荐度 |
|------|--------|--------|----------|--------|
| A. 降级到 Arduino-ESP32 2.x 旧版 | 极小 | 中（旧版也有 DHCP 问题） | 低 | ✗ |
| **B. 保持 Arduino，重写硬件驱动层** | **中** | **高** | **低** | **✓ 推荐** |
| C. 纯 ESP-IDF 重写 | 极大 | 最高 | 高 | ✗ |

### 决策：方案 B

**理由**：

1. 90% 的代码不需要改：状态机（`winder.cpp`）、JSON 协议（`protocol.cpp`）、存储（`storage.cpp`）、打滑检测（`slip.cpp`）、传感器（`sensors.cpp`）、Flutter APP 全部保持不变
2. 需要重写的只有三个硬件驱动文件 + 启动顺序
3. ESP-IDF 纯重写会变成 5 倍代码量，对于这个复杂度的项目不划算
4. 两个 Bug 的根因已经明确，定向修复即可

## 三、具体改动计划

### 3.1 LEDC 修复 — 舵机分辨率（`config.h` + `servo.cpp` + `servo.h`）

#### 改动点

**`config.h`**：

```c
// 改前
#define SERVO_RES_BITS  16

// 改后
#define SERVO_RES_BITS  14   // ESP32-S3 硬件上限 14 位
```

**`servo.cpp` — `begin()` 增加失败检测**：

```cpp
void ServoCtl::begin(uint8_t pin, uint16_t freq, uint8_t resBits) {
    if (_initialized) return;
    _pin = pin;
    _freq = freq;
    _resBits = resBits;
    _maxDuty = (1 << resBits) - 1;

    uint32_t actualFreq = ledcSetup(_channel, _freq, _resBits);
    if (actualFreq == 0) {
        Serial.printf("[Servo] LEDC 初始化失败! channel=%d freq=%d bits=%d\n",
                      _channel, _freq, _resBits);
        return;  // 不继续 attach，避免绑定无效通道
    }
    Serial.printf("[Servo] LEDC OK: channel=%d freq=%d bits=%d actualFreq=%d\n",
                  _channel, _freq, _resBits, actualFreq);

    ledcAttachPin(_pin, _channel);
    writePulse(_pulseStop);
    _direction = DIR_NONE;
    _position = 0;
    _initialized = true;
}
```

**duty 计算**（14 位下）：

```cpp
void ServoCtl::writePulse(uint16_t pulseUs) {
    // 20ms 周期（50Hz），pulseUs 范围 500-2500us
    uint32_t duty = (uint32_t)pulseUs * _maxDuty / 20000;
    ledcWrite(_channel, duty);
}
```

> 注意：原来用浮点 `(float)pulseUs / 20000.0f * _maxDuty`，改成整数乘除避免精度问题，且 14 位下 `65535 → 16383` 不会溢出 uint32_t。

### 3.2 WiFi 重写（`comms.cpp` + `comms.h`）

#### 核心原则

**去掉所有"聪明"的操作**，用最简单、最接近官方示例的方式初始化。当前代码的四层清理（disconnect → WIFI_OFF → delay → mode → softAPConfig → softAP → dhcps_start）反而破坏了 Arduino WiFi 的默认 DHCP 启动流程。

#### 新的 `wifiStartAP()`

```cpp
void Comms::wifiStartAP() {
    Serial.println("[WiFi] 启动 AP 模式");

    // 1. 设置模式（Arduino 内部会: 创建 netif → init wifi → start wifi → 启动 DHCP）
    WiFi.mode(WIFI_AP);
    delay(100);

    // 2. 启动 softAP（用默认 IP 192.168.4.1，默认子网 255.255.255.0）
    //    Arduino 的 WiFi.mode(AP) 已自动配置 DHCP，不要再用 softAPConfig 干扰
    bool ok = WiFi.softAP("ESP-Winder");
    Serial.printf("[WiFi] softAP: %s\n", ok ? "OK" : "FAIL");

    if (ok) {
        IPAddress ip = WiFi.softAPIP();
        Serial.printf("[WiFi] AP IP: %s\n", ip.toString().c_str());
        g_state.wifiConnected = true;
        g_state.wifiIP = ip.toString();
        g_state.wifiSSID = "ESP-Winder";

        // 3. 启动 TCP 服务器
        if (s_tcpServer) {
            s_tcpServer->stop();
            delete s_tcpServer;
        }
        s_tcpServer = new WiFiServer(WIFI_TCP_PORT);
        s_tcpServer->begin();
        Serial.printf("[WiFi] TCP: %s:%d\n", ip.toString().c_str(), WIFI_TCP_PORT);
    }
}
```

#### 新的 `begin()`

```cpp
void Comms::begin() {
    WiFi.onEvent(onWiFiEvent);
    // 不再调 WiFi.persistent(false) — 让 Arduino 用默认行为
    // 不再调 WiFi.setSleep(false) — 放到 softAP 之后

    bool staOk = wifiConnectSTA();
    if (!staOk) {
        Serial.println("[WiFi] 无凭据或 STA 失败，进入 AP 模式");
        wifiStartAP();
    }

    WiFi.setSleep(false);  // AP 启动后再关闭省电
}
```

#### 删除的内容

| 删除项 | 原因 |
|--------|------|
| `WiFi.persistent(false)` | 可能影响 netif 默认初始化路径 |
| `WiFi.disconnect(true,true)` + `WIFI_OFF` 清理 | 首次启动无需清理，反而打断 DHCP 启动 |
| `WiFi.softAPConfig(ip, gw, mask)` | Arduino 默认就是 192.168.4.1/24，无需覆盖 |
| `esp_netif_dhcps_start()` 手动调用 | Arduino `WiFi.mode(AP)` 已自动启动 DHCP |
| `esp_netif.h` 引用 | 不再需要底层 API |

#### DHCP 诊断事件保留

```cpp
case ARDUINO_EVENT_WIFI_AP_STAIPASSIGNED:
    Serial.printf("[WiFi] DHCP 分配 IP: %s\n",
        IPAddress(info.wifi_ap_staipassigned.ip.addr).toString().c_str());
    break;
```

如果修复后仍然看不到此事件，进入 3.5 节的备用方案。

### 3.3 初始化顺序重排（`main.cpp`）

#### 原则：先通信，后硬件

当前顺序的问题：硬件初始化失败（LEDC）→ 系统异常 → WiFi 初始化受影响。

**新的启动顺序**：

```
1. g_storage.begin()         →  加载配置（纯 NVS，不碰外设）
2. g_comms.begin()           →  WiFi 初始化（此时系统干净，无外设干扰）
3. g_winder.begin()          →  电机 + 舵机 + 传感器（即使 LEDC 失败也不影响 WiFi）
4. g_led.begin()             →  状态灯
5. g_winder.goHome()         →  寻原点
```

**`main.cpp` 改动**：

```cpp
void setup() {
    Serial.begin(115200);
    delay(1000);
    Serial.println("\n=== 耗材绕线器 ESP32-S3 ===\n");

    // 1. 配置
    Serial.println("[Main] 1/5 加载配置");
    g_storage.begin();
    g_storage.loadConfig(g_config);

    // 2. 通信（最先初始化，不受其他外设影响）
    Serial.println("[Main] 2/5 初始化 WiFi");
    g_comms.onMessage([](const String &msg) { g_protocol.handle(msg); });
    g_comms.begin();

    // 3. 硬件
    Serial.println("[Main] 3/5 初始化硬件");
    g_winder.begin();
    Serial.println("[Main] 硬件就绪");

    // 4. 状态灯
    Serial.println("[Main] 4/5 初始化状态灯");
    g_led.begin();

    // 5. 寻原点
    Serial.println("[Main] 5/5 寻原点");
    g_winder.goHome();

    Serial.println("[Main] 初始化完成\n");
}
```

### 3.5 备用方案：ESP-IDF 原生 WiFi（如果 3.2 仍未解决）

如果重写 `wifiStartAP()` 到最简形式后，DHCP 仍然不工作，则在 Arduino 框架内直接使用 ESP-IDF WiFi API，绕过 Arduino WiFi 类：

```cpp
#include "esp_wifi.h"
#include "esp_event.h"
#include "lwip/netif.h"

void wifiStartAP_idf() {
    // 1. 初始化 TCP/IP 协议栈
    ESP_ERROR_CHECK(esp_netif_init());

    // 2. 创建默认事件循环（Arduino 已创建，检查是否已存在）
    // esp_event_loop_create_default();

    // 3. 创建默认 AP netif（带 DHCP 服务器）
    esp_netif_create_default_wifi_ap();

    // 4. WiFi 初始化
    wifi_init_config_t cfg = WIFI_INIT_CONFIG_DEFAULT();
    ESP_ERROR_CHECK(esp_wifi_init(&cfg));

    // 5. 配置 AP
    wifi_config_t ap_config = {};
    strcpy((char*)ap_config.ap.ssid, "ESP-Winder");
    ap_config.ap.ssid_len = strlen("ESP-Winder");
    ap_config.ap.channel = 1;
    ap_config.ap.max_connection = 4;
    ap_config.ap.authmode = WIFI_AUTH_OPEN;

    ESP_ERROR_CHECK(esp_wifi_set_mode(WIFI_MODE_AP));
    ESP_ERROR_CHECK(esp_wifi_set_config(WIFI_IF_AP, &ap_config));
    ESP_ERROR_CHECK(esp_wifi_start());

    // DHCP 此时由 netif 自动启动
}
```

此方案保留 Arduino 框架（PlatformIO 编译不变），只替换 WiFi 初始化部分。TCP 服务器仍用 `WiFiServer`（底层仍是 lwip socket）。

## 四、验证步骤

### 4.1 LEDC 验证

1. 烧录后串口应显示：`[Servo] LEDC OK: channel=1 freq=50 bits=14 actualFreq=50`
2. 不再出现 `No more LEDC channels available` 错误
3. 舵机应能响应：发送左行/右行指令，舵机转动

### 4.2 WiFi 验证

1. 烧录后串口应显示：
   ```
   [WiFi] 启动 AP 模式
   [WiFi] softAP: OK
   [WiFi] AP IP: 192.168.4.1
   [WiFi] TCP: 192.168.4.1:8080
   ```
2. 手机连接 ESP-Winder 热点
3. 串口应显示：
   ```
   [WiFi-EVT] 设备已关联 MAC=... AID=1
   [WiFi] DHCP 分配 IP: 192.168.4.2
   ```
4. **手机应在数秒内获得 IP 地址**（状态栏显示"已连接"）
5. APP 填入 `192.168.4.1:8080`，TCP 连接成功
6. 串口显示 `[WiFi] TCP 客户端已连接: 192.168.4.2`

### 4.3 如果 DHCP 仍不工作

1. 检查是否为 iPhone（已知部分 iOS 版本对 ESP32 开放 AP 的 DHCP 有兼容问题）→ 换 Android 手机测试
2. 尝试给 AP 加密码：`WiFi.softAP("ESP-Winder", "12345678")`（WPA2）
3. 尝试换 WiFi 通道：`WiFi.softAP("ESP-Winder", NULL, 6)`（channel 6）
4. 提高 debug 级别：`platformio.ini` 中 `-DCORE_DEBUG_LEVEL=4`（DEBUG 级别），观察 IDF 层日志
5. 执行 3.5 节备用方案
